# 文章页面分阶段显示与加载性能分析

> 后续已按新的阅读交互要求切换为首屏优先、滚动逐字揭示与图表懒加载。当前实现见 [渐进阅读说明](./progressive-reading.zh-CN.md)。本文保留第一轮“整页组件完成后统一显示”的原因分析与验证记录，其中全量等待机制和相应耗时不再代表当前页面行为。

日期：2026-10-19。

验证页面：`/blog/automated-semver-version-tag-release-workflow`。

## 原因与证据

本问题不是移动端 UA 特有的服务端分支。相同问题在桌面浏览器也能复现；移动设备较低的脚本执行能力、移动网络、浏览器空闲调度差异，以及目录布局在客户端测量后才切换，使分阶段显示更加明显。

修改前在本机开发服务器，以 Edge 浏览器模拟 iPhone 13、中文环境逐帧采样：正文约 37ms 可见，约 5276ms 才出现移动目录按钮，13 张 Mermaid 图表约 7035ms 全部稳定。中途曾出现图表数量从 13 变为 0 再回到 13 的过程。上述时间从新文档执行采样脚本开始计算，属于单次本机复现数据，不代表线上性能分位数。

| 来源 | 原有行为 | 影响 |
| --- | --- | --- |
| `BlogPost.tsx` | 有服务端正文就直接视为 Done | 数据就绪被误当成页面整体就绪 |
| 目录与相关文章 | `requestIdleCallback`，最长等待约 1200ms；无支持时再等 200ms，随后请求相关文章 | 人为串行等待，目录与推荐列表后补 |
| `BlogPostMarkdown.tsx` | 每次渲染新建 Markdown 组件函数 | 父级更新时，代码块和图表可能重新挂载，重复解析与绘制 |
| Mermaid | 客户端动态导入后依次渲染 13 张图表 | 正文直出后，图表继续加载；销毁重建会再次付出成本 |
| 代码高亮 | 默认 Prism 引入所有语言 | 增加脚本下载、解析和初始化成本 |
| `ClientShell.tsx` | 首次刷新跳过遮罩；路由切换用 620ms 定时结束；部分组件动态加载时返回空占位 | 遮罩与真实组件生命周期无关，不能保证完成后再显示 |
| 全局 CSS | 外部字体 CSS 的 `@import` | 新增跨域样式请求和字体请求，受第三方服务及网络影响 |
| 国际化 | Provider 的服务端快照固定中文；页面按请求语言生成，同时未遵循关闭国际化的配置 | 首屏语言与客户端不一致，产生无效的正文及列表请求 |

此外，Windows 正文可能含 CRLF。渲染前统一换行符，同时明确不支持的代码语言按纯文本处理，避免服务端和客户端的文本及语法注册差异引发 hydration 失败，导致整棵文章树重新生成。

## 已实施的统一显示机制

`PageReadiness.tsx` 在文章详情路由生效，覆盖导航、正文、目录、页脚和播放器组件。服务端就输出加载界面，同时让真实页面保持 `visibility: hidden`，因此首帧不会提前露出正文；隐藏元素仍有正常布局尺寸，Mermaid 可以计算图表大小。

正文请求、相关文章和每个 Mermaid 实例通过 `usePageReadyTask` 登记待办任务。播放器的动态加载占位也登记任务，在真实组件挂载后释放。目录同步生成，页脚参与服务端渲染。待所有任务结束、连续两帧稳定，并完成当前视口图片的加载/解码与字体就绪检查后，整体切换为可见。固定的路由等待时间不再决定文章是否完成。

路由和语言变化会重新建立就绪检查；离开后返回同一文章也会重新等待。滚动恢复推迟到页面完成后，避免依据尚未生成图表的高度恢复阅读位置。

成功渲染和明确的错误回退都可以结束组件任务。Mermaid 加载失败时显示说明与源码；相关文章请求设置 8 秒超时。页面整体等待超过 15 秒时显示可重试界面，不会将未完成页面当成成功。禁用 JavaScript 时通过 `noscript` 显示服务端文章，保留基本阅读能力。

这里的完成范围是当前页面已挂载的组件与首屏图片。屏外正文图片仍然懒加载；未打开的图片预览、未选中的标签面板，以及用户主动播放时才需要的音频等资源，不阻塞整篇文章展示。等待全部屏外资源会使加载时间由最慢的第三方请求决定，也容易与懒加载互相阻塞。

## 已实施的速度优化

1. Markdown 使用 `React.memo`，组件映射使用 `useMemo`，目录操作和相关文章变化不再重建图表。
2. 目录从文章内容同步计算；相关文章在服务端读取，和正文读取同时启动。正常首屏不再请求 `/api/blog/list` 或重复请求 `/api/blog/post`。
3. Prism 改用轻量入口，仅注册常见且项目使用的语言；纯文本及未知语言直接显示。保留复制和行号。
4. 移除外部字体样式依赖，使用本机等宽字体，减少阻塞请求。没有安装 Roboto Mono 的设备会使用后备字体。
5. 页脚直接渲染，播放器保持代码拆分，但模块加载纳入就绪检查。
6. 国际化服务端快照使用服务端已解析的语言；服务端页面、元信息与布局共同遵守国际化开关。当前关闭国际化的配置下，英文浏览器也直接输出中文，不再先生成英文再请求中文。
7. 客户端正文和列表请求增加取消处理，避免快速切换时旧响应覆盖当前文章。

## 验证结果

生产构建使用项目实际生效的 `next.config.js`，启动独立的本机 3001 端口后测量，测试完成自动关闭该服务器。浏览器为本机 Edge Chromium，移动端使用 Playwright 的 iPhone 13 设备参数；这不等同于真实 iOS Safari 测试。

| 场景 | 页面统一显示 | 结果 |
| --- | --- | --- |
| 优化后，开发模式，移动端 | 约 1.63s | 目录及 13 张图表同时可见，无 hydration 错误 |
| 优化后，生产模式，移动端，无限速 | 约 1.04～1.50s | 正文出现时目录和 13 张图表均已完成 |
| 优化后，生产模式，桌面，无限速 | 一轮约 0.98s | 同上 |
| 优化后，生产模式，移动端，CPU 降速 4 倍 | 约 6.45s | 100ms 网络延迟，下载 750000 B/s，等待期间正文保持隐藏 |
| 优化后，生产模式，桌面，同样限速 | 约 7.36s | 无提前显示及脚本错误 |

这些是不同场景的观测值，不应用修改前的开发模式数据计算生产模式的提速比例。实际线上耗时还受缓存、压缩、CDN、设备及网络影响。

生产模式首屏观测到 JavaScript `transferSize` 合计约 2279427 字节；移动端 DOM 节点约 5655 个。这包含文章渲染、图表、共享组件及动态播放器等脚本，不是 Mermaid 单个包的大小。

自动化验证覆盖：服务端隐藏初始内容、等待全部任务、首屏图片错误回退、切换路由、返回同一文章、超时重试、其他路由不受影响，以及目录操作不重复挂载 Mermaid。浏览器另验证英文偏好与暗色模式（当前国际化关闭时仍应保持中文）和禁用 JavaScript 的阅读回退。另运行完整单元测试、TypeScript、Oxlint 和生产构建。

浏览器回归脚本为 `scripts/check-page-loading.cjs`，要求本机可使用 Playwright 和 Edge。可通过 `PLAYWRIGHT_MODULE` 指向已有 Playwright 模块，`PRODUCTION=1` 启用生产服务器，`SLOW=1` 启用上述限速参数。

## 后续性能空间

最值得进一步处理的是 Mermaid 的传输和计算成本。若要同时满足“所有图表完成后统一显示”和更短的低端设备等待时间，可以在内容更新或构建阶段预渲染、缓存图表 SVG，客户端只加载缩放与拖动交互。应分别处理明暗主题、SVG 安全清理、图表 ID 唯一性和缓存失效，避免引入主题或图表引用错误。这需要独立的内容构建流程，本次没有直接改变图表生成架构。

约 5600 个 DOM 节点说明长文本本身也有较高布局和 hydration 成本。进一步可以将 Markdown 解析和静态代码高亮迁至服务端，仅把复制、标签切换和图表交互保留为客户端组件。应先做拆分后的体积与耗时对照，再决定是否推进。

当前文章路由会读取 `cookies()` 和 `headers()`，生产构建标记为动态路由 `ƒ`，不能仅凭 `revalidate = 3600` 注释认定整页已经 SSG/ISR。若优化服务器响应，应把语言作为明确缓存维度设计，避免缓存错误语言。

仓库同时存在 `next.config.js` 与 `next.config.ts`；本次构建日志确认使用前者。后者的配置不能视为已经生效的性能措施。后续可单独合并配置，再验证构建和部署行为。
